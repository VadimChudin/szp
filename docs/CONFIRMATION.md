# Подтверждение зон по ликвидности

Экспериментальный слой. Отвечает на вопрос, который детектор зон не задаёт.

## Зачем

`zone_detector` ищет уровни по фитилям: место, где цена уже отбивалась. Это
правильный вопрос — «где был интерес». Но он не единственный.

Зона, построенная по теням двухнедельной давности, может стоять в ценовой
пустоте. Фитили никуда не денутся, структурный `score` останется высоким, а
уровень при этом мёртв: объём там больше не проходит, стопы под ним уже сняли.
Такая зона не отработает, сколько бы фитилей её ни формировало.

Слой подтверждения отвечает на второй вопрос — **жив ли уровень сейчас**.

## Почему не стакан

Первая мысль — взять биржевой стакан и посмотреть, стоят ли на уровне лимитные
заявки. Не выйдет, и не только по техническим причинам.

**Технически.** Ритейл-брокер не биржа. MT5 `market_book_get()` для CFD на
золото в подавляющем большинстве случаев возвращает пустоту либо синтетику
самого брокера. Настоящая книга по золоту живёт на COMEX и стоит денег.
Binance как обходной путь отпадает: `fapi.binance.com` отдаёт **HTTP 451
«Service unavailable from a restricted location»** — из РФ источник недоступен,
то есть у целевого пользователя он мёртв.

**По существу.** Даже с настоящей книгой она бы почти ничего не дала. Зоны
стоят в 200–900 пипсах от цены. Никто не держит лимиты так далеко, а те, что
стоят, снимаются задолго до подхода цены. Стакан описывает намерения на
ближайшие секунды — не на движение в $50.

Реальное подтверждение уровня даёт не книга заявок, а **история проторговки**:
где объём действительно прошёл и где остались неснятые скопления стопов.
Это же используют серьёзные системы — Volume Profile с POC/HVN/LVN и работа с
пулами ликвидности вместо угадывания по книге.

Скрипт `probe_liquidity.py` проверяет наличие стакана честным запросом к
терминалу, а не предположением. Если конкретный брокер его всё же отдаёт —
это будет видно, и книгу можно будет подмешать в подтверждение ближних зон.

## Как устроено

```
data_fetcher ──▶ volume_filter ──▶ zone_detector        (кандидаты: ГДЕ уровень)
                                        │
                                        ▼
                              zone_confirmation         (ЖИВ ЛИ уровень)
                                        ▲
                                        │
                                liquidity_source        (тики MT5 → MT4 → свечи)
                                        │
                                        ▼
                                  active_zones          (жизненный цикл H4)
                                        │
                                        ▼
                                   visualizer
```

Два новых модуля, три изменённых. Ни один существующий алгоритм не тронут:
детектор работает ровно как раньше, слой подтверждения только аннотирует его
результат.

### Разделение измерений

```
score        — структурная значимость уровня   (0..∞, целое)
confirmation — жив ли он прямо сейчас          (0..1, дробное)
```

Подтверждение **намеренно не складывается** со `score`. Одно суммарное число
замаскировало бы самый важный случай: сильный по структуре уровень в мёртвой
зоне. Инвариант закреплён тестом `test_confirmation_never_changes_structural_score`.

## Четыре проверки

| Проверка | Вес | Что измеряет |
|---|---|---|
| Узел объёма | 0.40 | Стоит ли зона на HVN или в пустоте (LVN) |
| Пул стопов | 0.25 | Есть ли рядом неснятые равные экстремумы |
| Дельта | 0.20 | Кто был агрессором на прошлых касаниях |
| Свежесть | 0.15 | Сколько раз уровень уже успели съесть |

Веса по принципу «чем прямее измерение, тем больше вес»: проторгованный
объём — факт из истории сделок, свежесть — производная оценка.

### Узел объёма — главный сигнал

Строим профиль объёма: распределение объёма **по цене**, а не по времени.
Это принципиально другой срез, чем свечной график, и получить его из одних
свечей нельзя.

Для зоны считаем, во сколько раз объём в её диапазоне превышает свою
**справедливую долю** — ту, что пришлась бы на этот диапазон при равномерном
распределении объёма по всей проторгованной истории.

- `≥ 1.5` — узел, там реально торговали → 1.0
- `≤ 0.5` — пустота, цена проходит транзитом → 0.0
- между — линейно

Зона на LVN не отработает почти никогда: там нет ни лимитных заявок, ни
истории сделок.

> **Почему справедливая доля, а не медиана.** Медиана кажется естественнее, но
> профиль сильно перекошен: большинство строк — хвосты, где цена побывала
> минуты и оставила крохи объёма. Медиана садится на эту крошку, и тогда
> обычный уровень выглядит узлом в тридцать раз плотнее нормы, а настоящая
> пустота — «средней». На синтетике с заранее заданной структурой медиана
> давала пустоте ×0.96 вместо ×0.20, то есть не отличала её от нормы вообще.
> Ошибку поймал тест `test_profile_separates_nodes_from_voids`.

### Пул стопов

Два и более примерно равных экстремума — скопление стопов. Под равными
минимумами толпа держит стопы лонгов, над равными максимумами — стопы шортов.
Пока пул не снят, он притягивает цену; после снятия аргумент исчезает.

Отсутствие пула — нейтраль (0.5), а не штраф: уровень может держаться на
одном проторгованном объёме. Штрафуем только уже снятый пул.

Алгоритм повторяет подход [`smartmoneyconcepts.liquidity`][smc] (★1.9k).
Реализован локально, чтобы не тянуть pip-зависимость в сборку PyInstaller.

### Дельта

Под ценой зона работает как поддержка — там должны были покупать. Над ценой
это сопротивление — там продавали. Совпадение знака означает, что уровень
держали реальными сделками, а не просто фитилём.

Требует источника, различающего агрессора (тики MT5). На свечном профиле
возвращаем нейтраль, а не выдумываем знак: аппроксимация дельты по `close-open`
даёт слишком много ложных срабатываний.

### Свежесть

Каждое касание расходует лимитные заявки на уровне. Первое встречает полную
книгу, третье — остатки. Считаем по H4 входы в зону, а не свечи внутри неё:
иначе одна консолидация даст десяток «касаний».

## Вердикт

```
score ≥ 0.65  →  LIVE    ✓   зона подтверждена
0.40 … 0.65   →  WATCH   ~   показываем, но не полагаемся
score < 0.40  →  DEAD    ✗   уровень мёртв
```

## Режимы

| Режим | Поведение |
|---|---|
| `off` | Слой выключен, поведение как до эксперимента |
| `annotate` | **По умолчанию.** Считаем и показываем, состав зон не меняем |
| `filter` | Зоны с вердиктом DEAD убираются |
| `rerank` | Кандидаты сортируются по `score × (0.5 + confirmation)` |

`annotate` стоит по умолчанию сознательно. Сначала нужно посмотреть, что
метрика показывает на реальном инструменте, сверить вердикты с тем, как зоны
отработали, и только потом давать ей право что-то отбрасывать.

В режиме `filter` есть страховка: если порог отсекает **все** зоны, фильтр не
применяется и возвращается исходный список. Пустой график хуже
неподтверждённых зон — трейдер остаётся без ориентиров и не понимает, сломался
индикатор или рынок такой.

## Порядок внедрения

```bash
# 1. Что вообще доступно у вашего брокера
python probe_liquidity.py

# 2. Посмотреть цифры, ничего не меняя
CONFIRMATION_MODE=annotate python main.py

# 3. Сверить вердикты с тем, как зоны отработали на графике

# 4. Откалибровать пороги под инструмент
HVN_RATIO=1.8 CONFIRM_DEAD_THRESHOLD=0.35 python main.py

# 5. Только теперь — фильтрация
CONFIRMATION_MODE=filter python main.py
```

## Настройки

Все через `.env`.

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `CONFIRMATION_MODE` | `annotate` | off / annotate / filter / rerank |
| `CONFIRMATION_IN_LABEL` | `1` | Метка «✓0.78» в подписи зоны |
| `LIQUIDITY_SOURCE` | `auto` | auto / ticks / bars |
| `TICK_HISTORY_DAYS` | `5` | Глубина тиковой истории |
| `MIN_TICKS_FOR_PROFILE` | `5000` | Меньше — профиль по тикам не строим |
| `HVN_RATIO` | `1.5` | Порог узла |
| `LVN_RATIO` | `0.5` | Порог пустоты |
| `CONFIRM_LIVE_THRESHOLD` | `0.65` | Порог вердикта LIVE |
| `CONFIRM_DEAD_THRESHOLD` | `0.40` | Порог вердикта DEAD |
| `LIQUIDITY_POOL_RANGE_PCT` | `0.005` | Допуск «равенства» экстремумов |
| `CONFIRM_WEIGHT_VOLUME_NODE` | `0.40` | Вес проверки по узлу |
| `CONFIRM_WEIGHT_LIQUIDITY_POOL` | `0.25` | Вес проверки по пулу |
| `CONFIRM_WEIGHT_DELTA` | `0.20` | Вес проверки по дельте |
| `CONFIRM_WEIGHT_FRESHNESS` | `0.15` | Вес проверки по свежести |

`TICK_HISTORY_DAYS` вынесен отдельно не случайно: сутки по золоту — сотни тысяч
тиков, запрос на месяц вешает терминал минутами.

## Что осталось за рамками

- **Сравнение с реальной отработкой.** Метрика построена на здравом смысле и
  проверена на синтетике. Как она соотносится с тем, отбилась ли цена от зоны
  на самом деле, ещё не измерено — для этого нужен прогон по `backtest.py`.
  До этого веса и пороги остаются гипотезой.
- **Стакан для ближних зон.** Если `probe_liquidity.py` покажет, что брокер
  книгу отдаёт, её имеет смысл добавить пятой проверкой — но только для зон
  ближе ~50 пипсов.
- **Свежесть считается по всей истории H4**, а не с момента формирования зоны.
  Для дальних зон разницы нет, для ближних оценка занижена.
