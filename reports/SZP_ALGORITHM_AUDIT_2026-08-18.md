# Технический аудит алгоритма Smart Zones Pro

**Дата:** 18 августа 2026 г.  
**Репозиторий и ветка:** `VadimChudin/szp`, `experiment/quality-first`  
**Проверенная ревизия:** `fd07952`  
**Объект аудита:** Python Core, MQL4/MQL5 Collector и StrongZones, файловый bridge, lifecycle H4, SL, сборка Experimental.  
**Вердикт:** алгоритм содержит несколько сильных инженерных идей, но текущий дефект отображения имеет **конкретную корневую причину в MQL-парсере JSON**. До её устранения любые изменения выбора зон в Python не способны гарантированно изменить то, что видно на графике.

## Исполнительное резюме

На реальном скриншоте подтверждён запуск нового бинарника индикатора: `SZP vExperimental-2.2.5-fd07952 | zones: 6`. Следовательно, проблема не сводится к устаревшему `.ex4/.ex5`. Однако скриншот одновременно показывает шесть жёлтых линий выше цены и не показывает `ref: ...`, хотя текущая версия Python Bridge обязана экспортировать это поле. Это означает, что отрисовываемый `zones_output.json` не соответствует ожидаемому контракту текущего Python Core: либо он был сформирован ранее/другим запущенным приложением, либо новый Bridge не выполнил успешный расчёт и синхронизацию.

Главная техническая причина неверных линий находится ниже Python-логики. В `StrongZones.mq4` и `StrongZones.mq5` список зон разбирается глобальным поиском каждого вхождения ключа `"price":`. У каждой настоящей зоны Bridge дополнительно записывает вложенный объект `sl`, у которого тоже есть ключ `"price"`. Поэтому MQL читает последовательность вида `zone.price → sl.price → следующая zone.price → следующая sl.price`, а затем останавливается после шести значений. В результате на график попадают три настоящие зоны и три цены SL, а не шесть топовых объектов из массива `zones`.

> **Ключевой вывод:** контракт `3 сверху + 3 снизу` может быть корректно выполнен Python Bridge, но MQL-парсер разрушает его после сериализации. Лимит `currentZoneCount < 6` ограничивает только число *прочитанных ключей*; он не гарантирует, что это шесть зон массива `zones`.

| Оценка | Статус | Значение |
|---|---:|---|
| Детекция структурных уровней | Условно жизнеспособна | Есть multi-timeframe, кластеризация и score, но нет эмпирической калибровки на production-данных. |
| Lifecycle H4 | Концептуально верен, реализация неоднозначна | Список сохраняется между пересчётами, однако положение относительно live price может меняться. |
| Контракт 3+3 в Python | Реализован, но не end-to-end доказан | Snapshot и final display guard пытаются соблюсти баланс. |
| Контракт Python → MQL | **Нарушен** | Наивный поиск `"price":` захватывает вложенный `sl.price`. |
| Достоверность текущей визуализации | Низкая | Нельзя интерпретировать все жёлтые линии как реальные зоны. |
| Готовность к торговому использованию | Низкая до P0 | Индикатор информационный, но ошибочная визуализация может искажать риск-решения. |

## 1. Зафиксированные наблюдения из реального терминала

Фрагмент метки, присланный пользователем, читается как `SZP vExperimental-2.2.5-fd07952 | zones: 6 | acc: 1 | 28m ago`. Он подтверждает, что терминал загрузил MQL-код из `exp-v2.2.5`, а число прочитанных MQL записей равно шести. При этом в строке отсутствует `ref: …`; в коде текущего MQL это поле выводится только когда в JSON присутствует числовой `reference_price`. Следовательно, визуализируемый payload не содержит нового поля либо не является результатом успешного расчёта текущего Bridge.

На полном скриншоте шесть жёлтых линий находятся над ценой. Это не опровергает Python final guard: MQL в текущей реализации не использует `display_side` и не проверяет, что прочитанные строки принадлежат top-level массиву `zones`. Вместо этого он глобально вычитывает первые шесть текстовых ключей `price` в документе.

| Наблюдение | Доказательство | Диагностическое следствие |
|---|---|---|
| Новый MQL-индикатор загружен | Build stamp `Experimental-2.2.5-fd07952` | Версия `.ex` не является единственной причиной. |
| MQL считает шесть элементов | `zones: 6` | Сработал лимит UI, но не подтверждена семантика этих шести элементов. |
| Нет `ref` в build stamp | В присланном фрагменте отсутствует `ref: …` | JSON устарел, сформирован старым Bridge или новая синхронизация не дошла до индикатора. |
| Все линии жёлтые | Полный скриншот | `is_fallback` не дошёл/не был корректно распознан; либо MQL читает не те объекты JSON. |

## 2. Архитектурная трассировка

Система имеет четыре логических слоя. Collector в MQL экспортирует OHLCV и тики в `Common/Files`; Python Bridge синхронизирует CSV, загружает данные, ищет кандидаты и создаёт `zones_output.json`; синхронизатор раскладывает этот JSON в `Common/Files` и локальные `MQL4/Files`/`MQL5/Files`; StrongZones читает файл и рисует линии. Архитектура допустима для desktop-индикатора, но файловый контракт должен быть строго версионирован и однозначно разбираем.

| Этап | Компонент | Фактическое поведение | Основной риск |
|---|---|---|---|
| 1 | `SmartZonesCollector.mq4/.mq5` | Экспортирует M1/H1/H4/D1, тики, live bid и имя символа каждые 30 секунд. | Имя файла зависит от точного broker symbol, например `XAUUSD`, `XAUUSDm` или `XAUUSD.a`. |
| 2 | `bridge_server.py` | Берёт данные из MT5 API/CSV, вызывает detector, lifecycle, normalizer, формирует JSON. | Несколько процессов приложения могут писать разные payload; новая мета может отсутствовать в старом JSON. |
| 3 | `sync_zones_to_mt4.py` | Копирует один JSON в Common и локальные Files **всех** обнаруженных терминалов. | Несколько терминалов получают один payload; MQL сначала читает Common, что маскирует локальный файл. |
| 4 | `StrongZones.mq4/.mq5` | Удаляет объекты `SZP_*`, наивно читает JSON и рисует до шести HLINE. | Глобальный парсер смешивает настоящие зоны и вложенные поля SL. |

### 2.1. Доказанная ошибка разбора JSON — P0

В MQL5 функция `ParseZonesJSON` ищет следующую позицию через `StringFind(json, "\"price\":", searchPos)` и увеличивает курсор на фиксированные десять символов. Затем `ExtractDouble` ищет `top`, `bottom`, `score` и `label` только *после этой позиции*, не ограничиваясь концом объекта зоны. Та же конструкция присутствует в MQL4.

Bridge добавляет к каждому `zone_data` объект `sl`, который создаётся из `StopCandidate.to_dict()` и содержит поле `price`. Это делает JSON структурно неоднозначным для текущего текстового сканера.

```json
{
  "price": 4700.00,
  "top": 4702.00,
  "bottom": 4698.00,
  "score": 12,
  "sl": {"side": "ABOVE_RESISTANCE", "price": 4720.00}
}
```

Репродуцируемый тест `reports/mql_parser_collision_proof.py` создаёт шесть корректных top-level зон с ценами `4700, 4750, 4800, 4500, 4450, 4400`. Эквивалентный MQL-сканер фактически получает первые шесть значений `4700, 4720, 4750, 4770, 4800, 4820`. Цены `4720`, `4770`, `4820` принадлежат вложенным объектам SL и не являются зонами.

> Это объясняет, почему Python-финализация баланса не дала ожидаемого эффекта: она нормализует массив `zones`, а MQL отображает не только его top-level цены.

### 2.2. Второй корневой фактор — stale/несогласованный payload

В `exp-v2.2.5` Bridge формирует top-level `reference_price`, а StrongZones выводит его в stamp как `ref: …`. На присланном фрагменте при том же build stamp этого поля нет. Это указывает на один из двух operational-сценариев: либо приложение Smart Zones Pro не было перезапущено после установки и продолжает Bridge старой сборки, либо индикатор читает файл, который не был заменён новой синхронизацией.

Файловый дизайн усиливает риск. MQL сначала пытается открыть `FILE_COMMON`, затем локальную папку; синхронизатор копирует JSON в Common и в папки всех найденных терминалов. При наличии нескольких MT4/MT5, старого процесса в трее или нескольких установочных каналов наблюдать «новый MQL + старый JSON» вполне возможно. Система не содержит обязательного поля `producer_build`, process lock, файла health-state или запрета отрисовки старой схемы.

## 3. Оценка алгоритма зон

### 3.1. Что сделано хорошо

Детектор извлекает верхние и нижние фитили на H1, H4 и D1, а затем объединяет уровни жадной кластеризацией. Это практичная и объяснимая базовая модель поддержки/сопротивления. Весовая система также прозрачна: H1/H4/D1 дают веса 2/3/4, большой объём добавляет 2, круглый уровень 1 и совпадение с H4 FVG 5. Уровень получает `touch_count`, источники и дополнительные признаки, что позволяет объяснять происхождение каждого кандидата.

Адаптивная ширина зоны — ещё одна сильная сторона. При `ZONE_WIDTH_MODE=atr` ширина ограничена диапазоном $0.50–$8.00 и строится на 14-period ATR H4. Это лучше фиксированной ширины на высоковолатильном золоте. Модель SL тоже отделена в независимый модуль: она использует структуру недавних swing и ATR-буфер, а не размещает произвольный стоп внутри зоны.

Lifecycle H4 пытается сохранить торговую семантику. Новые уровни не должны бесконечно перерисовываться внутри одной H4-свечи; замена ограничена одной стороной, слабый уровень уступает более сильному, а события сохраняются в журнале. Для зон «Titanic» есть архив с повторным подтверждением и отдельной логикой пробоя.

| Сильная сторона | Почему она полезна | Подтверждающий модуль |
|---|---|---|
| Multi-timeframe evidence | Уровень может получить подтверждение от H1, H4 и D1, а не от одного бара. | `zone_detector.py` |
| Объяснимый score | Баллы и источники можно показать пользователю и проверить в backtest. | `config.py`, `zone_detector.py` |
| ATR-bound width | Ограничивает чрезмерно широкие и чрезмерно узкие зоны. | `adaptive_zone_width()` |
| H4 lifecycle | Снижает визуальный шум и удерживает snapshot между закрытиями H4. | `active_zones.py` |
| Event log | Позволяет расследовать добавление, тест, замену и invalidation. | `zone_events.jsonl` |
| Архив значимых уровней | Сохраняет действительно сильные зоны, не сжигая их всей историей. | `persistent_zones.py` |
| Разделённая SL-модель | Вычисление объяснимо и не отправляет торговые приказы. | `sl_model.py` |

### 3.2. Что требует пересмотра

Фитиль считается значимым при 15% полного диапазона, хотя docstring всё ещё говорит о 30%. Это не только документационный долг: порог 15% увеличивает число слабых источников, а затем нагрузка переносится на фиксированную кластеризацию и score. Для XAU/USD абсолютный `CLUSTER_TOLERANCE=$5` также не масштабируется с волатильностью, хотя ширина зоны уже ATR-adaptive. В спокойном режиме $5 может склеивать несвязанные уровни, а в расширении рынка — наоборот дробить структуру.

Score не нормализован по числу баров и не декоррелирован между таймфреймами. H1/H4/D1 частично описывают одни и те же движения, но веса просто суммируются. Footprint POC/HVN добавляется в общий кластер как `has_volume=True`, что может резко усилить уровень без проверки качества/покрытия данных. Объём здесь — tick volume либо внешний footprint, поэтому score не является статистической вероятностью реакции.

Правило lifecycle `TEST_INVALIDATES_ZONE=true` по умолчанию слишком агрессивно для поддержки/сопротивления: подтверждённое касание часто является именно ожидаемой реакцией уровня, а не причиной немедленно убрать его. В то же время body breakout в persistent archive требует повторности, а active snapshot может удалить линию уже на первом тесте. Эти две политики конфликтуют и дают разные определения «актуальной зоны».

| Слабость | Практический эффект | Риск |
|---|---|---|
| Порог фитиля в коде 15%, в описании 30% | Сложнее калибровать сигнал и объяснять пользователю. | Средний |
| Абсолютный tolerance $5 | Качество кластеров зависит от режима волатильности. | Высокий |
| Суммирование correlated evidence | Score может завышать уверенность. | Высокий |
| Score не калиброван в вероятность | Цвет/ранжирование выглядит точнее, чем доказано. | Высокий |
| `TEST_INVALIDATES_ZONE=true` | Уровни исчезают после обычного касания. | Средний |
| Final display fallback | Выполняет UX-контракт, но projected уровень не является обнаруженной зоной. | Средний |
| Исторический archive | Может возвращать вне-контекстные уровни и усложнять reasoning. | Средний |

## 4. Lifecycle, 3+3 и fallback: почему логика стала хрупкой

Требование пользователя содержит две полезные, но конфликтующие цели: обновлять состав зон только после закрытия H4 и одновременно всегда держать три линии по каждую сторону от **текущей** цены. За время одной H4-свечи цена может перейти через несколько ранее верхних или нижних уровней. Если snapshot заморожен, визуальная сторона естественно изменится; если автоматически перестраивать список внутри H4, нарушается требование стабильности.

В текущей реализации это решается двумя слоями: persisted H4 snapshot и export-only `normalize_display_balance`. Идея оправдана, но её нужно явно формализовать. Persisted snapshot должен хранить реальные активные уровни и обновляться только на H4 close. Display layer может заменять только недостающие визуальные слоты projected fallback-линиями, не меняя archive/active state. Эти fallback обязаны быть красными, иметь отдельное поле `kind: "display_fallback"` и не участвовать в score, invalidation, Telegram и backtest как реальные зоны.

Пока MQL не читает надёжный JSON, этот раздел не может быть проверен на терминале. После исправления P0 нужно добавить bridge-level invariant test: готовый JSON содержит шесть **top-level** объектов, три имеют `zone_price > reference_price`, три имеют `zone_price < reference_price`, а каждая projected fallback зона явно имеет `is_fallback=true`.

## 5. Stop-loss: расхождение двух моделей

Python `sl_model.py` строит объяснимый StopCandidate: определяет сторону по `current_price` относительно зоны, берёт swing за 40 баров и ATR(14), применяет buffer `max(0.25*ATR, 0.35*width)`. Это хороший фундамент для аналитической подсказки.

Но MQL StrongZones игнорирует экспортированный `sl` объект и пересчитывает собственный SL локально из текущего chart timeframe. Поэтому в продукте существуют две разные SL-модели: Python экспортирует одну цену в JSON, MQL рисует другую. Более того, именно экспортированный, но неиспользуемый `sl.price` ломает текущий MQL-парсер зон.

**Решение:** выбрать один source of truth. Рекомендуется Python SL-модель с `stop_price` и MQL-отображение только этого значения. MQL не должен повторно рассчитывать ATR/swing для той же зоны. Это устранит split-brain и уберёт источник коллизии ключей.

## 6. Тесты, сборка и пробелы в валидации

На ветке присутствуют 155 Python-тестов. Покрыты detector, FVG, volume filter, data fetcher, config, persistent zones, lifecycle, backtest helpers, SL и статические MQL display-contract проверки. Windows CI действительно компилирует MQL4/MQL5, строит PyInstaller и Inno Setup, что является сильной практикой delivery.

Однако тесты почти полностью модульные. `test_bridge_server.py` покрывает только чтение timeframe-флага Footprint; нет теста `calculate_and_export_zones()` с реальным JSON, nested SL, reference price, копированием в terminal Files и разбором этого же payload парсером MQL. Статические проверки строк MQL не способны обнаружить семантическую ошибку глобального `StringFind`.

| Проверка | Текущий статус | Требуемое дополнение |
|---|---|---|
| Python detector/lifecycle | Есть unit tests | Добавить property tests на side balance для random price moves. |
| JSON schema | Нет | Добавить Pydantic/JSON Schema и `schema_version`. |
| Python → MQL parsing | Нет | Golden payload test: шесть zones + nested stop; MQL-equivalent parser обязан вернуть ровно шесть zone_price. |

| Multiple terminals/processes | Нет | Process lock, health file, deterministic terminal targeting. |

## 7. Приоритетный план исправления

### P0 — блокирующее исправление до следующего теста пользователя

Нужно заменить неформальный JSON-контракт. В top-level объекте зоны использовать уникальные ключи: `zone_price`, `zone_top`, `zone_bottom`, `zone_score`, `zone_fallback`; в стопе — `stop_price`. MQL должен сканировать только `"zone_price":` и не искать общий `"price":`. Правильнее всего использовать компактный строгий парсер массива `zones`, но даже уникальные ключи немедленно устранят доказанную коллизию.

Bridge должен добавить поля `schema_version`, `producer_build`, `payload_id`, `reference_price`, `reference_source` и атомарно записывать JSON. StrongZones обязан отказаться рисовать зоны, если `schema_version` не поддерживается, `reference_price` отсутствует или `producer_build` не совпадает с ожидаемой совместимой схемой. Вместо молчаливых жёлтых линий stamp должен показывать красную ошибку `STALE / INCOMPATIBLE PAYLOAD`.

### P1 — сделать runtime наблюдаемым и однозначным

Нужно ввести single-instance lock для SmartZonesPro и файл `bridge_health.json`: PID, `producer_build`, timestamp, активный symbol, источник данных, reference price, payload id, число real и fallback зон. UI должен показывать эти данные в панели диагностики. Синхронизация должна целиться в выбранный терминал, а не безусловно копировать payload во все MT4/MT5. В настройках нужно явно выбрать активный терминал и активный chart symbol.

### P2 — развести domain-model и display-model

Persisted snapshot должен содержать только реальные зоны и события lifecycle. Display fallback должен существовать только в экспортном DTO, иметь `kind=display_fallback`, не попадать в persistent database, score calibration, Telegram-сигналы и backtest как реальная зона. Тогда требование стабильности H4 и требование визуального 3+3 не будут конфликтовать.

### P3 — повысить качество самой модели

Следует перевести cluster tolerance из фиксированных $5 в ATR-relative tolerance по H4, убрать противоречие 15%/30% wick threshold, нормализовать score по независимым подтверждениям и калибровать score на walk-forward out-of-sample данных. Перед любыми торговыми рекомендациями нужно построить отчёт по hit rate, invalidation rate, MAE/MFE и ожидаемой реакции для bucket-ов score, volatility regime и стороны уровня.

## 8. Рекомендуемая последовательность восстановления

Первым действием не следует снова менять score или выпускать новую визуальную палитру. Сначала нужно исправить P0 JSON/MQL schema и добавить golden integration test. Затем нужно принудительно обновить schema version, чтобы старый `zones_output.json` был отвергнут, а не отрисован. После этого пользователь должен запустить только один экземпляр приложения, дождаться health/payload stamp с актуальными `producer_build`, `ref` и `payload_id`, и прислать один скрин.

Только когда на реальном терминале подтверждены шесть **корректно распарсенных** top-level зон, имеет смысл калибровать detector. В противном случае изменения в H4 lifecycle, fallback и score оцениваются по графику, который не отображает переданные Python объекты.

## Заключение

SZP уже имеет хорошую основу: multi-timeframe detector, ATR-width, явный lifecycle, журналы событий, archive и CI-сборку. Но система стала слишком сложной вокруг интерфейса Python ↔ MQL, не зафиксировав строгий schema contract. Текущий пользовательский симптом не является вопросом «мало свечей» или «неверный score». Это **ошибка сериализации/разбора**, усугублённая отсутствием runtime-observability и однозначного producer identity.

До P0 нельзя доверять видимому составу шести линий и нельзя интерпретировать их как три реальных уровня сверху и три снизу. После P0 и end-to-end test можно вернуться к качеству детекции и доказательной калибровке score.
